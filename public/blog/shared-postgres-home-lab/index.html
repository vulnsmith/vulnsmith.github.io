Moving Application Databases to Shared PostgreSQL

Consolidating databases reduced duplicated operational work, but it also made isolation, backups, credentials, and upgrade planning explicit responsibilities.

Jack SmithSeptember 15, 2026Platform operations notes

Running a database beside every application is a reasonable starting point. The application and its data share a lifecycle, the connection string is simple, and a Helm chart can create everything in one release. As the home lab grew, that convenience turned into repetition: more database containers, more credentials, more backup jobs, more upgrade paths, and more storage attached to workloads that otherwise did not need it.

I moved the application databases onto a shared PostgreSQL service. The goal was not to pretend that one database server was a magical source of high availability. The goal was to centralize the database engine while preserving application-level boundaries and making the operational work consistent.

Shared Does Not Mean Mixed Together

The first design decision was the isolation model. Each application received its own database and login, with only the privileges required by that application. A shared PostgreSQL instance is a platform service; it is not a reason for applications to share a superuser, schema, or password.

BoundaryPurpose
DatabaseSeparates application objects, extensions, and backups at the logical level.
RoleLimits which application can connect and what it can do.
SecretKeeps credentials independently rotatable and scoped.
Network policyLimits which workloads can reach PostgreSQL at all.
Backup recordIdentifies the owner, restore order, and retention requirements.

Database separation is useful, but it is not a complete security boundary against a compromised PostgreSQL administrator or a server-level failure. That limitation belongs in the design instead of being hidden behind the word “shared.”

Inventory the Old Database Contract

The migration was not just a data export. Each application had an implicit contract with its old database: hostname, port, database name, username, password format, extensions, collation, schema ownership, migrations, and expected connection limits. I wrote those assumptions down before changing them.

This exposed a common trap. An application may start successfully after a connection-string change while still failing later when it runs its first migration, creates an index, or executes a feature that depends on a PostgreSQL extension. Compatibility needs to be tested by application behavior, not just by whether the container became ready.

Choose the Migration Method by Risk

For small databases, a logical dump and restore was the most understandable path. It produced an artifact that could be inspected, stored with the backup process, and restored into a clean database before cutover. Larger or busier workloads may justify replication or a short final synchronization, but complexity should match the actual downtime requirement.

  1. Create the target database and least-privilege role.
  2. Restore a representative dump into a clean target.
  3. Run the application's migrations and validation checks against the target.
  4. Schedule a brief write pause for the final export.
  5. Restore the final data, reset ownership and privileges, and update the application secret.
  6. Start the application and verify reads, writes, background jobs, and migrations.
  7. Keep the old database available but read-only until the rollback window closes.

The write pause was the important part. Exporting a live database and immediately switching clients can lose transactions that arrived after the dump began. A clear cutover boundary is easier to reason about than an optimistic assumption that the application was quiet enough.

Credentials Became Platform Objects

When databases were bundled with applications, credentials tended to follow the application deployment. Shared PostgreSQL made it more important to model them explicitly. Each application secret contained only its own connection details, and the PostgreSQL service account used for administration was separate from application roles.

Rotation also became a planned operation. Create a new role or password, update the encrypted secret, restart or reload the consumer, verify connections, and revoke the old credential after the overlap period. That sequence is less disruptive than discovering during an incident that every application depends on one shared password.

Network reachability remained narrow. Only namespaces and workloads that needed PostgreSQL received a path to the service. Authentication and authorization inside PostgreSQL complemented, rather than replaced, Kubernetes network policy and firewall controls.

Backups Had to Follow the Data

Moving databases onto shared PostgreSQL changed where the backup responsibility lived. Application volumes were no longer the complete backup. The PostgreSQL data directory, logical database exports, role definitions, extension requirements, and restore order all mattered.

I treated physical and logical recovery as different tools. A physical backup can restore the PostgreSQL service efficiently. Logical dumps are valuable for individual database recovery, migration testing, and portability. Both need retention, monitoring, and restore tests. A backup job that reports success without proving that a database can be opened and queried is not enough evidence.

The recovery question

Can I restore one application's database without restoring every application's state, and can I rebuild the PostgreSQL service without the cluster that hosted it?

The Shared Failure Domain Is Real

Consolidation reduced the number of database engines to maintain, but it increased the impact of a PostgreSQL outage. A maintenance mistake, storage failure, incompatible upgrade, or exhausted connection pool could affect several applications at once.

That tradeoff made observability more important. I monitored database readiness, storage health, connection usage, replication or backup status where applicable, slow queries, failed authentication, and per-database activity. Connection limits were considered at the service level rather than allowing every application to consume the server's available connections independently.

Shared infrastructure also needs an upgrade policy. PostgreSQL major-version upgrades are migrations, not ordinary image updates. Application compatibility, extension support, dump and restore testing, rollback limits, and the maintenance window need to be known before the production service is replaced.

What I Would Keep Separate

Not every database belongs on the shared service. A workload with unusual extensions, incompatible version requirements, extreme resource behavior, strict isolation needs, or a lifecycle that should not depend on the platform database may be better served by its own instance.

The useful boundary is operational, not ideological. Shared PostgreSQL is a good default when the applications have compatible requirements and the platform can provide reliable backups, monitoring, access control, and recovery. It is a poor default when “one less container” is the only reason for choosing it.

Lessons Learned

The migration made the database engine a real platform dependency. That was a benefit because upgrades, backups, monitoring, and access patterns became consistent. It was also a warning because the blast radius became larger and had to be managed deliberately.

The successful design was not simply one PostgreSQL server for many applications. It was one service with separate databases, separate roles, separate secrets, narrow network access, explicit backup ownership, and a tested restore path. Centralization reduced repetition; it did not eliminate responsibility.
