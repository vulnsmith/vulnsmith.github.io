Moving Kubernetes Storage to Longhorn: The PVC Was Not the Data

Migrating persistent workloads from node-bound storage to Longhorn was less about changing a StorageClass and more about proving that data, identity, and recovery still lined up afterward.

Jack SmithSeptember 15, 2026Storage migration notes

The first k3s workloads used persistent volume claims backed by storage that was effectively tied to where a pod happened to run. That was enough to get services online, but it made rescheduling and maintenance uncomfortable. A node could be healthy from Kubernetes' perspective while the volume a workload needed remained somewhere else—or could not be attached anywhere else at all.

Longhorn gave the cluster a storage layer designed for Kubernetes rather than a collection of local directories. It added replicated volumes, a Kubernetes-native management model, snapshots, backups, and the ability to attach a volume to another node. The important lesson was that Longhorn improved the storage failure model; it did not remove the need for backups or restore tests.

A PVC Is a Request, Not the Data

The migration became much clearer after separating four things that are easy to treat as one object:

ObjectWhat it representsMigration question
PodThe process using the storageCan it stop cleanly and start elsewhere?
PVCThe application's request for storageWhich claim name and access mode must remain stable?
PVThe binding between the claim and a volumeCan the existing data be copied or reattached safely?
Volume dataThe files, database pages, and application stateHow will integrity be verified after the move?

Changing a manifest to storageClassName: longhorn does not move the bytes in an existing volume. It can create a new empty volume, leave the old data behind, or fail to bind depending on the claim and provisioner state. A storage migration is therefore a data operation with Kubernetes coordination around it.

Inventory Before Cutover

I started by mapping every persistent workload to its claims, mount paths, data type, and recovery method. Stateless deployments could be ignored. A media directory, an application upload path, and a database volume could not be treated as interchangeable simply because all three appeared as PVCs.

The inventory also recorded whether a workload could tolerate downtime, whether it had an application-level export, and whether its data was already protected outside the cluster. Longhorn replication protects against some node and disk failures; it does not protect against an application deleting its own records, a bad migration, or an operator removing the volume.

The useful question

Do not ask only, “Is this PVC bound?” Ask, “What exact state must exist for this service to recover, and how will I prove it?”

Designing the Longhorn Layer

Longhorn introduced choices that local storage had hidden. Replica count, disk and node scheduling, recurring snapshots, backup targets, and the amount of capacity reserved for rebuilding replicas all affect the result. More replicas improve availability only when they are placed across genuinely different failure domains.

Three replicas on three Kubernetes nodes that share one Proxmox host are not three independent copies during a hypervisor failure. The cluster still benefits from node-level recovery, but the physical placement must be understood before calling it highly available.

I kept the storage class and volume settings explicit in the Git-managed cluster configuration. That made the intended default visible, while allowing workloads with different durability or performance needs to request their own policy. Storage should be a platform decision with application-specific exceptions, not an unexplained chart default.

The Migration Pattern

For each workload, the safe sequence was to prepare the destination, stop writes, copy or restore the data, point the workload at the new claim, and validate the application before declaring success. The exact copy mechanism depends on the workload. File-oriented data can be copied with a temporary transfer pod or a backup tool. Databases should generally use a database-consistent dump or replication method rather than copying live database files underneath a running process.

  1. Record the current claim, mount path, owner, and backup status.
  2. Test the existing backup or export before touching production data.
  3. Provision the Longhorn-backed claim with the intended size, access mode, and policy.
  4. Stop the application or place it into a mode that prevents writes.
  5. Transfer or restore the data into the new volume.
  6. Deploy the application against the new claim and verify ownership, permissions, and file integrity.
  7. Exercise the service from the outside, then retain the original volume until the migration has a rollback window.

The rollback detail matters. Deleting the old claim immediately turns a migration mistake into a recovery exercise. Keeping the source intact for a defined period made the cutover reversible without pretending that two volumes could safely receive writes at the same time.

What Longhorn Changed Operationally

After migration, a node drain no longer automatically meant that a workload had to wait for the original disk location. Longhorn could detach and attach the volume elsewhere, subject to replica health and the workload's access mode. That made maintenance more predictable.

It also added a new set of things to monitor: degraded replicas, rebuild activity, available capacity, replica scheduling failures, engine or instance-manager health, and backup freshness. A volume being attached is not the same as a volume being healthy. I treated a degraded volume as an incident to resolve, not as a harmless status color.

Snapshots Are Not Backups

Longhorn snapshots are useful for short-term rollback and fast local recovery. They still live inside the storage system and can share the same cluster, host, or administrative failure as the source volume. Backups to a separate target are what provide a different recovery boundary.

The recovery test was deliberately broader than checking that a snapshot existed. I restored a volume, mounted it to a clean workload, and verified that the application could read the expected data. For databases, that also meant checking the database's own consistency and running application-level queries. A backup that cannot be restored is only an intention.

Lessons Learned

The migration succeeded because it was planned as a data move, not a YAML change. Kubernetes resources described how the workload should consume storage; they did not guarantee that the old bytes would appear in the new volume.

Longhorn made the cluster more flexible, but it did not make storage magical. Placement, capacity, replica health, backup separation, application consistency, and restore testing still determine whether persistent services are resilient. The best outcome was not merely that pods could move. It was that I could explain where their state lived, how it was protected, and how to bring it back.
